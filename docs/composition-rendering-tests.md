# 百纹成画位图恢复测试修复与验收

日期：2026-10-23。本次仅修改测试与文档，未新增依赖；作品存储、恢复、拼接渲染及其他业务代码保持原样。

## 已知问题已关闭：测试条件不一致

旧四模式脚本直接在交互画布上约 1600 次调用 getImageData，再继续交互、保存和重绘。该读取影响 Chrome 的 Canvas 渲染后端；恢复页面创建新的默认上下文，保存前后抗锯齿条件不同。旧断言以 toDataURL 字符串完全一致作为恢复正确性的依据，因此失败。

诊断使用 Chrome 129.0.6668.100，实测元素 ID、位置、大小、旋转、颜色及顺序一致。1024 × 1024 图像有 2022 个像素、6097 个通道值不同，最大通道差值 139；没有全透明与全不透明互换。保存前图像与显式 CPU 渲染完全一致，恢复图像与新默认上下文完全一致。对恢复画布大量读取并再次用相同数据重绘后，与保存前图像完全一致。不是单纯 PNG 编码不同，也不是保存数据丢失。

只将逐点读取改为一次批量读取的早期对照仍失败，因此正式修复没有仅靠减少读取，更没有简单放宽误差阈值。

## 验证分层

1. **真实模型的数据恢复**：保存时记录完整 document；恢复后通过 UI 再次保存实际编辑模型，使用 Node deepStrictEqual 比较所有字段及元素顺序，同时确认作品 ID 不变。不是只重读未变的 localStorage 来推断恢复成功。默认场景用两个独立元素覆盖顺序，并在恢复后继续拖动其中一个，检查另一个元素不变。
2. **确定性位图**：通过 Chrome CDP 在新页面脚本前，且仅在拼接页面的 paper-canvas 首次 getContext 时注入 willReadFrequently: true。保持前后条件一致，解码 PNG 后比较尺寸和全部 RGBA 通道，零容差。原恢复断言没有跳过；编码字符串比较改为实际像素比较。
3. **默认上下文集成**：移除注入，再新开拼接页面，确认上下文属性与原生新画布一致。实际执行添加、移动、缩放、旋转、换色、保存、恢复、继续编辑及前后 PNG 下载。两次下载的 PNG 解码后全部 RGBA 通道严格一致。页面与 2048 导出的已有不透明/透明内部采样标准不变，另验证透明背景与不含选框。

像素采样从交互画布的独立解码快照读取，一次读取后在数组中比较；不会在交互画布上循环 getImageData。严格位图比较的离屏解码画布显式选择读取友好的上下文。Chrome 129 的 getContextAttributes 中 willReadFrequently 返回字符串，检查会规范化表示，不用布尔值硬比较。

测试结束（包括失败）移除新文档注入并恢复原测试存储；报告写明 outcome、failure、分层计数、浏览器版本、下载记录及异常。BASE_URL 支持指定测试服务器。页面加载检查包括查询参数，并明确处理缺失作品恢复后 URL 自动清理的情况。
